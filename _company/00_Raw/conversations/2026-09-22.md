### 🔥 3. Paywall 핵심 구매 유도 헤드라인 (3가지 버전)
사용자가 '지금 돈을 내지 않으면 이 기회를 영원히 놓칠 것 같다'는 강렬한 FOMO(Fear Of Missing Out)를 느끼게 합니다.

#### **Version A: 긴급성/위기감 강조형 (The Urgency Trigger)**
*   **헤드라인:** ⏰ 마감 임박: 당신의 여정은 지금 '비효율적'으로 설계되고 있습니다.
*   **서브 카피:** 이대로 계획을 확정하면, 최소 [N]시간 이상의 기회비용 손실이 발생합니다. 최적화된 경로를 확인하고 시간을 확보하세요.
*   **CTA 버튼:** 💡 시간과 돈을 아끼는 방법 보기 (Premium)

#### **Version B: 손실 회피/수치화 강조형 (The Loss Aversion Trigger)**
*   **헤드라인:** 당신이 놓친 $T_{loss}$: 무료 플랜은 최소 [N]만원, [M]시간의 가치를 포기하게 합니다.
*   **서브 카피:** 일반적인 검색으로는 절대 찾을 수 없는 숨겨진 '최적화 비용'이 있습니다. 이 손실액을 방지하려면 업그레이드가 필수입니다.
*   **CTA 버튼:** 🛡️ 모든 리스크를 막는 플랜 구매하기

#### **Version C: 권위/희소성 강조형 (The Exclusivity Trigger)**
*   **헤드라인:** [Expert Only]: 진정한 여행자는 '최단 거리'가 아닌, '시간 가치'로 여정을 설계합니다.
*   **서브 카피:** 시간과 돈을 아끼는 전문가들만 사용하는 비공개 로직입니다. 당신의 다음 여행을 최상으로 끌어올릴 단 하나의 도구.
*   **CTA 버튼:** ✨ 전문가 모드 활성화하기 (Premium)

### 🧱 II. 핵심 컴포넌트 세트 (3가지 상태)

#### 1. [API/데이터 누락 에러] - Missing Data Error
*   **상황:** 사용자가 요청한 데이터 조합으로는 최적의 경로를 계산할 수 없는 경우. (가장 흔함)
*   **목표:** '정보 부족'을 '결제 필요'로 치환한다.
*   **구조:** 경고 아이콘 ➡️ 헤드라인(손실 고지) ➡️ 본문(원인 설명 + 손실 지표 제시) ➡️ CTA (해결책).

| 요소 | 내용/카피 예시 | 비주얼 처리 및 가이드 |
| :--- | :--- | :--- |
| **제목** | 🔴 놓치고 있는 최적 경로가 있습니다. | `#CC3333` + `⚠️` 아이콘 사용. 가장 크고 두드러지게 배치. |
| **본문 (원인)** | 현재 설정된 필터 조건($X$ 지역, $Y$ 기간)만으로는 최소 10시간 이상의 최적 여정을 계산할 수 없습니다. 이로 인해 예상되는 **최소 손실 기회비용은 ₩XXX,XXX** 입니다. | '손실 지표'는 `#CC3333`으로 강조 처리. (ex: $\text{Loss} \approx \$250$) |

| **CTA 버튼 B** | (선택 사항) 필터 조건 완화 및 재시도 | 보조 액션(Secondary Action). 회색 처리하여 가치를 낮춤. |

*   **구조:** 경고 아이콘 ➡️ 헤드라인(제한 고지) ➡️ 본문(근본 원인 제시 + 가이드 제공) ➡️ CTA (단계별 접근 유도).

| 요소 | 내용/카피 예시 | 비주얼 처리 및 가이드 |

| **CTA 버튼** | **[추천: 지역 A와 B로 나누어 분석하기]** | 사용자가 다음 단계로 나아갈 구체적인 가이드라인을 제시하며 CTA를 만듦. (가장 중요한 것은 '다음에 무엇을 해야 하는지' 명확히 알려주는 것) |

| 요소 | 내용/카피 예시 | 비주얼 처리 및 가이드 |

<replace>
const calculateSavings(dataA: PathData | null | undefined, dataB: PathData | null | undefined): { savingsMinutes: number; savingsCost: number } {
    // 데이터가 아예 없거나 비교 불가능한 경우 0으로 초기화하여 안정성을 확보합니다.
    if (!dataA || !dataB) {
        return { savingsMinutes: 0, savingsCost: 0 };
    }

    const a = dataA; // Type narrowing for safety
    const b = dataB;

    // 필수 속성이 누락되었을 경우 (Null/Undefined 체크 강화)
    const travelTimeA = a?.travelTime ?? Infinity;
    const travelTimeB = b?.travelTime ?? Infinity;
    const costA = a?.cost ?? 0;
    const costB = b?.cost ?? 0;

    return {
        // Math.max(0, ...)를 통해 음수 손실 계산을 방지합니다.
        savingsMinutes: Math.max(0, travelTimeA - travelTimeB),
        savingsCost: Math.max(0, costA - costB)
    };
}
</replace>

### 💻 최종 분석 보고서 및 코드 제안 (Analysis Report)

**보고자:** 코다리 (시니어 풀스택 엔지니어)
**대상:** CEO/개발팀
**문제 영역:** `comparisonLogic` 통합 테스트 실패 (`exit 1`)
**발견된 근본 원인:**
테스트 실패의 핵심은 **'방어적 프로그래밍(Defensive Programming)' 부재**였습니다. 기존 로직은 입력 데이터(`PathData`)가 필수 속성(예: `travelTime`, `cost`)을 가지고 있을 것이라는 '낙관적인 가정(Optimistic Assumption)'에 의존했습니다. 실제로는 API 응답이나 Mock Data에서 해당 속성이 `null`이거나 아예 정의되지 않은 경우(`undefined`)가 발생할 수 있으며, 이 상태로 수학적 연산자나 객체 접근을 시도하면서 런타임 오류가 발생했습니다.

**핵심 결함:**
1.  **Null/Undefined 취약성:** 데이터 구조의 비대칭성에 대한 체크가 부족하여, `null` 또는 `undefined` 값을 가진 변수를 산술 연산에 사용했을 때 시스템이 강제 종료되었습니다.
2.  **테스트 커버리지 누락:** 가장 흔한 실패 케이스인 '데이터 미완성' 상태를 테스트 시나리오에서 제외했습니다.

**✅ 적용된 수정 사항 (패치):**
1.  `src/services/ComparisonService.ts`: `calculateSavings` 함수에 **타입 가드(Type Guard)** 로직을 도입하여, 모든 입력 데이터가 유효한지 확인하고, 필수 속성(`travelTime`, `cost`)이 누락되었을 경우 기본값으로 처리하거나 비교를 건너뛰도록 수정했습니다.
2.  `tests/comparisonLogic.test.ts`: '데이터 미완성(Incomplete Data)' 및 '전체 데이터 부재' 상황에 대한 **3가지 경계 조건 테스트 케이스**를 추가하여 안정성을 확보했습니다.

이 패치와 구조 개선을 통해, 서비스는 기술적 오류가 아닌 **'정보의 손실 가능성'**이라는 비즈니스 관점의 결핍으로 실패를 처리할 수 있게 되었습니다.

**발견된 근본 원인:**
테스트 실패의 핵심은 **'방어적 프로그래밍(Defensive Programming)' 부재**였습니다. 기존 로직은 입력 데이터(`PathData`)가 필수 속성(예: `travelTime`, `cost`)을 가지고 있을 것이라는 '낙관적인 가정(Optimistic Assumption)'에 의존했습니다. 실제로는 API 응답이나 Mock Data에서 해당 속성이 `null`이거나 아예 정의되지 않은 경우(`undefined`)가 발생할 수 있으며, 이 상태로 수학적 연산자나 객체 접근을 시도하면서 런타임 오류가 발생했습니다.

**핵심 결함:**
1.  **Null/Undefined 취약성:** 데이터 구조의 비대칭성에 대한 체크가 부족하여, `null` 또는 `undefined` 값을 가진 변수를 산술 연산에 사용했을 때 시스템이 강제 종료되었습니다.
2.  **테스트 커버리지 누락:** 가장 흔한 실패 케이스인 '데이터 미완성' 상태를 테스트 시나리오에서 제외했습니다.

**✅ 적용된 수정 사항 (패치):**
1.  `src/services/ComparisonService.ts`: `calculateSavings` 함수에 **타입 가드(Type Guard)** 로직을 도입하여, 모든 입력 데이터가 유효한지 확인하고, 필수 속성(`travelTime`, `cost`)이 누락되었을 경우 기본값으로 처리하거나 비교를 건너뛰도록 수정했습니다.
2.  `tests/comparisonLogic.test.ts`: '데이터 미완성(Incomplete Data)' 및 '전체 데이터 부재' 상황에 대한 **3가지 경계 조건 테스트 케이스**를 추가하여 안정성을 확보했습니다.

## 1. 크레딧 정의 및 산출 공식 (Credit Quantification)

**개념:** `Insight Credit`은 단순히 '사용 가능 횟수'가 아닙니다. 이는 사용자가 **만족할 만한 깊이 있는 인사이트를 얻을 수 있는 잠재적 가치 단위($V_{insight}$)**입니다. 분석의 복잡도와 결과 도출의 신뢰도가 높을수록 더 많은 크레딧이 소모됩니다.

### 💡 핵심 산출 공식
1.  **소모 크레딧 ($C_{cost}$):** $\text{Ceiling} (\frac{\text{요구되는 분석 깊이 지수}(D)}{\text{크레딧 당 기본 측정 단위}(U)})$
    *   $D$: 사용자가 현재 요청한 보고서의 복잡도 (예: A는 1.0, B는 3.5)
    *   $U$: 플랜별 크레딧이 커버하는 분석 깊이 상수 (플랜에 따라 다름)

2.  **총 가치 ($V_{total}$):** $C_{\text{initial}} \times U_{plan} \times R_{rate}$ (초기 구매 크레딧 $\times$ 플랜별 측정 단위 $\times$ 환율/비중)

### 💲 플랜별 비교 및 산출 규칙

| 구분 | Basic Plan ($9.99/월) | Pro Plan ($29.99/월) | 비즈니스 가치 포인트 (BVP) |
| :--- | :--- | :--- | :--- |
| **크레딧 제공량** | 100 $V_{insight}$ 단위 (10~15회 분석 가능) | 350 $V_{insight}$ 단위 (40~50회 분석 가능) | Pro는 Basic 대비 **최소 2배 이상**의 핵심 가치를 제공해야 함. |
| **$U_{plan}$ (단위 깊이)** | 1.0 ($9.99 / \text{분석 기능}$) | 3.5 ($29.99 / \text{분석 기능}$) | Pro는 단일 분석 기능을 실행할 때도 Basic보다 높은 $V_{insight}$를 부여하여 **'가치 압도'** 효과 창출. |
| **주요 제한 조건** | 단일 목적지/단기 일정 비교 보고서에 최적화 (Depth < 2.0) | 다중 지역/장기 트렌드 분석, 비용-효율성 시뮬레이션 가능 (Depth $\ge$ 3.5) | Basic은 '문제 발견'에 초점, Pro는 '해결책 제시 및 예측'에 초점. |

***[테스트 가이드]***

## 2. 손실 지표 (Loss Metric) 정량화 및 Paywall 로직 정의

사용자가 크레딧 부족 또는 기능 제한에 도달했을 때, 시스템은 기술적 실패를 **"놓치고 있는 기회비용($T_{loss}$)"**으로 변환해야 합니다.

### 🔴 핵심 Loss Metric (Error State Trigger)

| 에러/제한 시나리오 | 비즈니스 원인 (Why?) | $T_{loss}$ 계산 및 제시 로직 | UI 컴포넌트 역할 |
| :--- | :--- | :--- | :--- |
| **1. 크레딧 부족** | 분석 깊이($D$)가 현재 크레딧으로 커버할 수 있는 최대치를 초과함. | $T_{loss} = (\text{실제 필요한 } D) - (C_{\text{잔여}} \times U)$<br>예: "추가 50%의 분석 깊이가 필요하며, 이는 약 \$X에 해당하는 가치입니다." | **CTA:** 'Insight Credit 추가 구매하기'와 함께 $T_{loss}$ 수치를 강조. |
| **2. API 요청 제한 초과** | 단순한 시스템 부하 문제가 아닌, 사용자가 너무 많은 *미성숙* 데이터를 한 번에 처리하려 함. | $T_{loss} = \text{남은 일일 할당량 대비 남은 분석 기회비용}$.<br>예: "오늘 하루 3개의 핵심 시뮬레이션이 더 가능합니다." | **CTA:** '다음 날 재개' 또는 'Pro Plan으로 무제한 확보하기'. |
| **3. 최적 경로 없음 (Edge Case)** | 단순 데이터 누락이 아니라, 사용자가 놓치고 있는 **대안적인 고효율 경로**가 존재함. | $T_{loss} = \text{최적화된 대안 비용}(\text{Optimal}) - \text{현재 선택지 예상 비용}(\text{Current})$.<br>예: "직접 계산하신 것보다, 이 노선을 이용하면 **\$45의 시간/비용을 절약**할 수 있습니다." | **CTA:** '전문가 분석 보고서로 최적화하기' (Advanced Report). |
