# 💰 bosstak: Insight Credit 시스템 V2.0 최종 비즈니스 스펙

## 1. 크레딧 정의 및 산출 공식 (Credit Quantification)

**개념:** `Insight Credit`은 단순히 '사용 가능 횟수'가 아닙니다. 이는 사용자가 **만족할 만한 깊이 있는 인사이트를 얻을 수 있는 잠재적 가치 단위($V_{insight}$)**입니다. 분석의 복잡도와 결과 도출의 신뢰도가 높을수록 더 많은 크레딧이 소모됩니다.

### 💡 핵심 산출 공식
1.  **소모 크레딧 ($C_{cost}$):** $\text{Ceiling} (\frac{\text{요구되는 분석 깊이 지수}(D)}{\text{크레딧 당 기본 측정 단위}(U)})$
    *   $D$: 사용자가 현재 요청한 보고서의 복잡도 (예: A는 1.0, B는 3.5)
    *   $U$: 플랜별 크레딧이 커버하는 분석 깊이 상수 (플랜에 따라 다름)

2.  **총 가치 ($V_{total}$):** $C_{\text{initial}} \times U_{plan} \times R_{rate}$ (초기 구매 크레딧 $\times$ 플랜별 측정 단위 $\times$ 환율/비중)

### 💲 플랜별 비교 및 산출 규칙

| 구분 | Basic Plan ($9.99/월) | Pro Plan ($29.99/월) | 비즈니스 가치 포인트 (BVP) |
| :--- | :--- | :--- | :--- |
| **크레딧 제공량** | 100 $V_{insight}$ 단위 (10~15회 분석 가능) | 350 $V_{insight}$ 단위 (40~50회 분석 가능) | Pro는 Basic 대비 **최소 2배 이상**의 핵심 가치를 제공해야 함. |
| **$U_{plan}$ (단위 깊이)** | 1.0 ($9.99 / \text{분석 기능}$) | 3.5 ($29.99 / \text{분석 기능}$) | Pro는 단일 분석 기능을 실행할 때도 Basic보다 높은 $V_{insight}$를 부여하여 **'가치 압도'** 효과 창출. |
| **주요 제한 조건** | 단일 목적지/단기 일정 비교 보고서에 최적화 (Depth < 2.0) | 다중 지역/장기 트렌드 분석, 비용-효율성 시뮬레이션 가능 (Depth $\ge$ 3.5) | Basic은 '문제 발견'에 초점, Pro는 '해결책 제시 및 예측'에 초점. |

***[테스트 가이드]***
*   **Basic Plan 사용:** $C_{cost}$가 소모됨과 동시에, **"이 분석으로는 3가지 변수를 고려할 수 없습니다."** 와 같은 제한 메시지를 노출해야 합니다.
*   **Pro Plan 사용:** Basic에서 부족했던 영역(예: 날씨 예측 통합, 비수기/성수기 트렌드 비교)을 한 번에 제공하여 **'이것 없이는 안 된다'**는 경험적 인식을 심어야 합니다.

## 2. 손실 지표 (Loss Metric) 정량화 및 Paywall 로직 정의

사용자가 크레딧 부족 또는 기능 제한에 도달했을 때, 시스템은 기술적 실패를 **"놓치고 있는 기회비용($T_{loss}$)"**으로 변환해야 합니다.

### 🔴 핵심 Loss Metric (Error State Trigger)

| 에러/제한 시나리오 | 비즈니스 원인 (Why?) | $T_{loss}$ 계산 및 제시 로직 | UI 컴포넌트 역할 |
| :--- | :--- | :--- | :--- |
| **1. 크레딧 부족** | 분석 깊이($D$)가 현재 크레딧으로 커버할 수 있는 최대치를 초과함. | $T_{loss} = (\text{실제 필요한 } D) - (C_{\text{잔여}} \times U)$<br>예: "추가 50%의 분석 깊이가 필요하며, 이는 약 \$X에 해당하는 가치입니다." | **CTA:** 'Insight Credit 추가 구매하기'와 함께 $T_{loss}$ 수치를 강조. |
| **2. API 요청 제한 초과** | 단순한 시스템 부하 문제가 아닌, 사용자가 너무 많은 *미성숙* 데이터를 한 번에 처리하려 함. | $T_{loss} = \text{남은 일일 할당량 대비 남은 분석 기회비용}$.<br>예: "오늘 하루 3개의 핵심 시뮬레이션이 더 가능합니다." | **CTA:** '다음 날 재개' 또는 'Pro Plan으로 무제한 확보하기'. |
| **3. 최적 경로 없음 (Edge Case)** | 단순 데이터 누락이 아니라, 사용자가 놓치고 있는 **대안적인 고효율 경로**가 존재함. | $T_{loss} = \text{최적화된 대안 비용}(\text{Optimal}) - \text{현재 선택지 예상 비용}(\text{Current})$.<br>예: "직접 계산하신 것보다, 이 노선을 이용하면 **\$45의 시간/비용을 절약**할 수 있습니다." | **CTA:** '전문가 분석 보고서로 최적화하기' (Advanced Report). |

## 3. Mock Payment API 테스트 시나리오 정의 (E2E Test Suite 기준)

개발팀이 `CreditManager`와 결제 로직을 연동 검증할 수 있도록, 성공 및 실패 케이스의 입력/출력값을 명확히 정의합니다.

### ✅ A. 성공 시나리오: 크레딧 구매 및 사용
*   **입력:** Payment Token (Basic Plan) + 요청 $D$ 값 = 3.0
*   **기대 비즈니스 동작:** `CreditManager`가 Basic Plan ($U=1.0$)에 따라 $\text{Ceiling}(3.0 / 1.0) = 3$ 크레딧을 차감해야 함.
*   **Mock API 응답 (Success):** `{ status: "success", credits_deducted: 3, new_balance: 7, report_data_unlocked: true }`

### ❌ B. 실패 시나리오 1: 크레딧 부족 (Critical Failure)
*   **입력:** Payment Token (없음) + 요청 $D$ 값 = 5.0
*   **기대 비즈니스 동작:** 현재 잔액으로 커버 불가. 결제 게이트웨이 호출 없이, `CreditManager`가 즉시 $T_{loss}$ 객체를 생성해야 함.
*   **Mock API 응답 (Failure):** `{ status: "insufficient_credits", required_depth: 5.0, loss_metric_value: 2.0, message: "최적 분석에 필요한 Insight Credit이 부족합니다." }`

### ⚠️ C. 실패 시나리오 2: 결제 게이트웨이 오류 (External Failure)
*   **입력:** Payment Token (유효하지 않은 형식/승인 거절 카드). 요청 $D$ 값 = 3.0
*   **기대 비즈니스 동작:** 크레딧 차감 **X**. 트랜잭션 실패 메시지 출력. 사용자에게 재시도 또는 플랜 변경 유도.
*   **Mock API 응답 (Failure):** `{ status: "payment_declined", error_code: "PAY-403", message: "결제 수단 승인에 실패했습니다. 다른 카드를 시도해 주세요." }`
