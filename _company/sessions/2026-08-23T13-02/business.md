코다리 에이전트의 통합 테스트 결과를 면밀히 검토했습니다. 우선, `test_data_period_expired` 시나리오에서 **'데이터 오류'가 발생한 것**은 단순한 기술적 실패를 넘어선, 치명적인 비즈니스 논리 결함입니다. 사용자가 가장 필요로 하는 순간에 신뢰를 잃는 최악의 경험입니다.

저희 서비스의 핵심 가치는 'Hidden Cost(숨겨진 비용)'와 'Loss Aversion(손실 회피)'에 기반하고 있습니다. 따라서 모든 예외 처리 로직은 시스템 결함이 아닌, **사용자가 현재 놓치고 있는 기회비용**을 제시하는 방향으로 설계되어야 합니다.

현재 테스트 결과에서 발견된 핵심 문제점을 바탕으로, 제가 검토한 누락된 비즈니스 Edge Case 3가지와 이를 코다리에게 전달할 최종 지시 사항을 정리했습니다. 이 시나리오들은 단순 데이터 부족이 아니라, '비즈니스가 처리해야 하는 예외 상황'에 초점을 맞춥니다.

### 🔍 [현빈의 Edge Case 검토 및 추가 요청]
**수신:** 코다리 (💻 Developer)
**주제:** Mock Service Layer 통합 테스트 시나리오 보강 (Critical Business Logic Focus)

#### 1. 핵심 실패 지점 수정: '정보 결핍' 메시지 강제화 (P0 - Immediate Fix)
*   **문제:** 데이터 만료 시 HTTP 500 에러 반환 (`test_data_period_expired` failure).
*   **요구사항:** 이 오류는 **시스템 오류가 아님**을 전제로 해야 합니다. 백엔드에서 `PeriodExpiredError(412 Precondition Failed)`와 같은 비즈니스 예외 코드를 명시적으로 반환해야 하며, 이 응답 구조에는 반드시 사용자에게 전달할 '손실 정의' 카피(`Loss Aversion Message`)가 포함되어야 합니다.
*   **테스트 액션:** `test_data_period_expired`의 기대값(Expected)을 **기술적 성공/실패 여부가 아닌, 비즈니스 로직 기반 응답 구조 및 내용**으로 수정하고 재실행해야 합니다.

#### 2. 누락된 Edge Case A: '최적 경로 없음' 시나리오 (P1 - New Logic)
*   **비즈니스 상황:** 사용자가 지정한 출발지-도착지 간에, 서비스가 정의하는 '합리적인 연결'을 가진 경로 자체가 존재하지 않는 경우 (예: 특정 시간대에 폐쇄된 노선, 지나치게 비효율적인 환승 지점만 존재하는 등).
*   **기존 테스트의 한계:** 현재는 데이터가 없으면 에러로 처리되거나, 단순히 '결과 없음'으로 끝납니다. 이는 사용자에게 무력감을 줍니다.
*   **요구하는 로직:** 시스템은 최소한의 비용을 들여 **'차선책(Fallback Option)'** 경로를 강제로 계산하여 제시해야 합니다. (예: "최적 경로는 아니지만, 현재 시점 기준 가장 빠르거나 저렴한 대안입니다.")
*   **테스트 데이터 필요:** Mock Data에 '실제 존재하지만 비효율적인' 대체 경로 데이터를 포함하고, 이 경로가 최적으로 계산되도록 로직을 테스트해야 합니다.

#### 3. 누락된 Edge Case B: '과도하게 복잡한 조합 요청' 시나리오 (P1 - New Logic)
*   **비즈니스 상황:** 사용자가 API 호출 시 너무 많은 파라미터(예: 출발 시간, 도착 시간, 예산 상한선, 선호하는 이동 수단 3가지 등)를 동시에 넣었으나, 이 모든 조건이 **동시에 만족되는 경로가 없는 경우.**
*   **기존 테스트의 한계:** 일반적인 API 유효성 검사(Validation) 수준에서 처리되고, 사용자에게 어떤 정보가 부족했는지 명확히 안내하지 못합니다.
*   **요구하는 로직:** 시스템은 "모든 조건을 만족시키는 최적 경로를 찾을 수 없습니다. 혹시 **이 조건(예: 예산 상한선)**을 풀면 어떨까요?"와 같이, *조건 자체의 조정 필요성*을 사용자에게 역으로 제안해야 합니다.
*   **테스트 데이터 필요:** 논리적으로 불가능하지만 형식적으로는 유효한 파라미터 조합 세트가 필요합니다.
