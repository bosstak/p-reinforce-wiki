# 📜 bosstak Advanced Trip Planner: 최종 통합 비즈니스 계약서 (V1.0)

**문서 버전:** 1.0
**작성자:** 현빈 (Head of Business Strategy)
**목표:** '정보의 부족함/손실 가능성($T_{loss}$)'을 핵심 수익화 동력으로 하는 크레딧 기반 서비스 로직 확정 및 개발팀 핸드오버.

## Ⅰ. 핵심 비즈니스 플로우차트 (Flowchart & Logic Map)

시스템이 요청 처리를 시작하고 종료할 때까지의 모든 과정을 단계별로 정의합니다.

```mermaid
graph TD
    A[시작: 사용자 서비스 이용 시도] --> B{요청 유효성 검사};
    B -- 실패(Input Error) --> C[UI 표시: 일반 에러 메시지 (빨강 계열)];
    B -- 성공 --> D{Insight Credit 보유 여부 확인};
    D -- N/A 또는 < 1 크레딧 --> E[비즈니스 로직 실행 불가];
    E --> F[시스템 응답: Loss Metric 계산 및 전송];
    F --> G[UI 표시: '크레딧 부족' 손실 경고 (빨강 계열, $T_{loss}$ 명시)];
    G --> Z[종료: 유료 전환 유도];

    D -- 성공 & 충분 크레딧 --> H{경로 비교 로직 실행};
    H --> I{최적 경로 발견 여부?};
    I -- 실패 (데이터 부족) --> J[비즈니스 로직 실행 불가];
    J --> F; % 손실 메시지 계산으로 연결

    I -- 성공 --> K[1. 결과 데이터 산출];
    K --> L[2. Insight Credit 차감 요청];
    L --> M{결제 시스템 응답};
    M -- 실패 (DB/API Error) --> N[시스템 에러 처리: $T_{loss}$ 계산 및 전송];
    N --> G;

    M -- 성공 & 크레딧 차감 완료 --> O[최종 UI 표시: 최적 경로 비교 결과 + 남은 크레딧];
    O --> Z;
```

## Ⅱ. 정량적 요구사항 (Quantitative Requirements)

### 1. 핵심 메트릭 정의 및 계산 (The Loss Metric, $T_{loss}$)
*   **정의:** 사용자가 시스템의 제약(크레딧 부족, 데이터 부족 등)으로 인해 얻지 못하고 놓치게 된 잠재적인 최대 가치.
*   **계산 공식:** $T_{loss} = (\text{최적 경로 비용}) - (\text{현재 상황에서 제공 가능한 최저 수준 정보의 가치})$
    *   `Optimal_Cost`: 만약 크레딧이 충분했다면 사용자에게 제시되었을 '진짜' 최대 절감액 (가정값).
    *   `Current_Value`: 현재 무료로 볼 수 있는 기본 데이터의 비용/정보량.
*   **데이터 전송 요구사항:** $T_{loss}$ 값은 반드시 **소수점 둘째 자리까지의 숫자** 형태로 프론트엔드에 전달되어야 합니다. (예: `123.45`)

### 2. 크레딧 차감 로직 (Credit Deduction Logic)
*   **원칙:** 모든 핵심 비교 분석(최적 경로 제시 등)은 **비동기적으로** API 호출 및 트랜잭션으로 처리되어야 합니다.
*   **Success Case:** `Credit_Balance` $\ge$ `Cost_per_Report`. 차감 성공 시, 백엔드는 반드시 다음 두 값을 포함하여 응답해야 합니다: `{ success: true, remaining_credits: N-1 }`.
*   **Failure Case (Insufficient Credit):** `Credit_Balance` $< $ `Cost_per_Report`. **절대로 크레딧을 차감하지 않습니다.** 대신 Loss Metric 계산 플로우를 즉시 트리거합니다.

### 3. 경계 조건 및 예외 처리 목록 (Edge Cases & Error Handling)
| ID | 상황/트리거 | 발생 시 동작 로직 | $T_{loss}$ 연관성 | UI 컴포넌트 요구사항 |
| :--- | :--- | :--- | :--- | :--- |
| EC-01 | **크레딧 부족** | API 호출 차단. Loss Metric 계산 실행. | 높음 (가장 직접적인 손실) | 빨강 경고, "아직 2개의 기회가 남아있습니다." 등 유료 전환 CTA 포함. |
| EC-02 | **입력 데이터 누락** | 경로 A 또는 B의 필수 파라미터(예: 시간대, 교통수단)가 누락됨. | 중간 (정보의 불완전성 손실) | 빨강 경고, "최적화를 위해 [누락된 정보]를 추가해 주세요." |
| EC-03 | **API 호출 제한 초과** | 백엔드 측에서 외부 서비스(예: 지도 API) 요청 횟수 제한에 걸림. | 높음 (기술적 제약으로 인한 손실) | 빨강 경고, "시스템 과부하 상태입니다. 잠시 후 다시 시도하거나 Pro Plan을 이용해 우선권을 확보하세요." |
| EC-04 | **데이터 계산 실패** | 비즈니스 로직(예: 최단 경로 알고리즘 자체의 오류)이 런타임 에러를 발생시킴. | 중간 (시스템 신뢰성 손실) | 빨강 경고, "현재 시스템 내부 처리 중 오류가 발생했습니다. $T_{loss}$ 계산을 통해 잠재적 기회비용을 알려드립니다." |

## Ⅲ. 최종 승인 체크리스트 (Acceptance Checklist for Kodari Agent)

이 항목들은 코다리 에이전트가 테스트 케이스(`e2e_comparison_suite.test.ts`)를 작성할 때 반드시 검증해야 할 **최종 요구사항**입니다.

### 🟢 Happy Path Test Case: 성공적인 비교 및 차감
*   **GIVEN:** 사용자 A는 유효한 출발지/도착지를 입력했고, 크레딧 잔액은 `3`이다.
*   **WHEN:** 사용자가 'Advanced Report' 생성을 요청한다.
*   **THEN (Pass):** 시스템은 API를 성공적으로 호출하고, 결과 데이터를 산출하며, 백엔드는 **크레딧을 1 차감**했음을 확인해야 한다.
*   **AND THEN:** UI는 최종 결과를 보여주며, 남은 크레딧이 `2`임을 명확히 표시해야 한다.

### 🟡 Warning Path Test Case: 크레딧 부족 (EC-01)
*   **GIVEN:** 사용자 B는 유효한 출발지/도착지를 입력했고, 크레딧 잔액은 `0`이다.
*   **WHEN:** 사용자가 'Advanced Report' 생성을 요청한다.
*   **THEN (Pass):** 시스템은 API 호출을 차단하고, 백엔드는 **크레딧 변화 없이** 응답해야 한다.
*   **AND THEN:** UI는 빨간색 경고와 함께 $T_{loss}$ 값을 명시하며, 유료 업그레이드 CTA가 최상단에 노출되어야 한다.

### 🔴 Edge Case Test Case: 데이터 계산 실패 (EC-04)
*   **GIVEN:** 사용자 C는 복잡한 이동 경로를 입력했으나, 백엔드 로직에서 예상치 못한 계산 오류(예: 무한 루프 방지 타이머 초과 등)가 발생한다.
*   **WHEN:** 'Advanced Report' 생성을 시도한다.
*   **THEN (Pass):** 시스템은 일반적인 500 에러 대신, **$T_{loss}$ 계산 모듈을 통해 오류 원인으로 인한 손실액을 산출하여 사용자에게 전달**해야 한다.
*   **AND THEN:** 이 과정에서 크레딧 차감 시도는 발생해서는 안 된다.
